## 2. DCP mechanics (archived evidence)

- **Compress tool**: DCP reduces context size through a compress tool and automatic cleanup. Compress is a tool exposed to the model that replaces closed, stale conversation content with high-fidelity technical summaries - framed by the README as "a much smarter version of Opencode's compaction process": instead of triggering statically at max context on the entire session, Compress lets the model pick when to activate based on task completion and compress only the specific messages no longer needed verbatim (sources/dcp-github-readme.md).
- **Request-message mutation vs stored-session untouched**: "Your session history is never modified - DCP replaces pruned content with placeholders before sending requests to your LLM." The mutation happens on the outbound request messages only; the stored session is not rewritten (sources/dcp-github-readme.md).
- **Two compression modes**: `range` mode compresses contiguous spans of conversation into one or more summaries (overlapping new compressions nest inside earlier ones so information is preserved through layers); `message` mode (experimental) compresses individual raw messages independently for more surgical control. Default mode is `range` (sources/dcp-github-readme.md, sources/dcp-schema.json compress.mode).
- **Deduplication strategy**: identifies repeated tool calls (same tool, same arguments) and keeps only the most recent output. Recalculated when the compress tool runs, "so prompt cache is only impacted alongside compression" (sources/dcp-github-readme.md; sources/dcp-schema.json strategies.deduplication, enabled default true).
- **purgeErrors strategy**: prunes inputs from errored tool calls after a configurable number of turns (default 4); error messages are preserved, only the potentially large input content is removed. Recalculated on compress tool use (sources/dcp-github-readme.md; sources/dcp-schema.json strategies.purgeErrors, enabled default true, turns default 4).
- **Protected tools**: by default these tools are always protected from pruning: `task`, `skill`, `todowrite`, `todoread`, `compress`, `batch`, `plan_enter`, `plan_exit`, `write`, `edit`. The `protectedTools` arrays in `commands` and `strategies` add to this default list. For the compress tool, `compress.protectedTools` ensures specific tool outputs are appended to the compressed summary (default: `task`, `skill`, `todowrite`, `todoread`). `protectUserMessages` preserves user messages verbatim during compression, at the cost that large prompts (e.g. pasted log files) are never compressed away (sources/dcp-github-readme.md; sources/dcp-schema.json).
- **Triggers**: automatic nudges fire above `compress.maxContextLimit` (default 100000 tokens or "X%"; nudgeFrequency default 5, nudgeForce soft/strong) and turn/iteration reminders above `minContextLimit` (default 50000; iterationNudgeThreshold default 15). Slash commands `/dcp` (TUI panel with context, stats, manual-mode controls) and `/dcp-compress [focus]` (one compression pass) provide manual triggers. `manualMode.enabled` disables autonomous context management so tools only run when explicitly triggered (sources/dcp-schema.json; sources/dcp-github-readme.md).
- **Config surface (dcp.schema.json)**: `enabled`, `autoUpdate`, `debug`, `pruneNotification` (off/minimal/detailed), `pruneNotificationType` (chat/toast), `commands` (enabled, protectedTools), `manualMode` (enabled, automaticStrategies), `turnProtection` (enabled, turns), `experimental` (allowSubAgents, customPrompts), `protectedFilePatterns`, `compress` (mode, permission, showCompression, summaryBuffer, maxContextLimit, minContextLimit, modelMaxLimits, modelMinLimits, nudgeFrequency, iterationNudgeThreshold, nudgeForce, protectedTools, protectTags, protectUserMessages), `strategies` (deduplication, purgeErrors). Config file search order: global `~/.config/opencode/dcp.jsonc`, then `$OPENCODE_CONFIG_DIR/dcp.jsonc`, then project `.opencode/dcp.jsonc`; each level overrides the previous (sources/dcp-schema.json; sources/dcp-github-readme.md).
- **Package/repo facts**: npm dist-tags latest=3.1.14, beta=3.2.8-beta0; author tarquinen; AGPL-3.0-or-later license; GitHub Actions trusted publisher (sources/opencode-dcp-npm-registry.json, sources/opencode-dcp-3.1.14-manifest.json). ## 3. Cache economics: the 85% vs 90% claim and the cost asymmetry

- **The vendor claim**: DCP's README states: "LLM providers cache prompts based on exact prefix matching. When DCP prunes content, it changes messages, which invalidates cached prefixes from that point forward." It then frames the trade-off ("You lose some cache reads but gain token savings from reduced context size and fewer hallucinations from stale context") and asserts: "In testing, cache hit rates were approximately 85% with DCP vs 90% without." (sources/dcp-github-readme.md).
- **Unquantified nature**: the 85% vs 90% figure is a single sentence with no methodology, no sample size, no provider breakdown, no date, and no confidence bounds - "approximately" and "In testing" are the only qualifiers. It is vendor self-reported, not a benchmark. The researcher's independent search for benchmarks failed (DuckDuckGo bot challenge; gh_grep found none) - see section 9. No third-party measurement of DCP's cache impact exists in the archived evidence.
- **DeepSeek 50x miss/hit**: DeepSeek V4 Flash direct pricing: 1M input tokens cache hit $0.0028 vs cache miss $0.14 - a 50x ratio; output $0.28/1M. Peak/off-peak billing takes effect 16:00 UTC 2026-08-16: off-peak hit $0.007 / miss $0.22 (~31x), peak hit $0.014 / miss $0.44 (~31x) (sources/deepseek-pricing.md).
- **DeepSeek cache mechanics**: caching is enabled by default; a request only hits the cache if it FULLY matches a persisted cache prefix unit (Sliding Window Attention changed matching from prefix-overlap to whole-unit matching); units are persisted at request boundaries (end of user input and end of model output), via common-prefix detection across requests, and at fixed token intervals for long inputs/outputs; the cache is "best-effort" with no 100% hit-rate guarantee; unused cache is cleared within hours to days (sources/deepseek-kv-cache.md).
- **Go subscription cached-token dominance**: OpenCode Go's typical DeepSeek V4 Flash request is 790 input + 68,000 cached + 280 output tokens per request (sources/opencode-go-docs.md). The DIA-183 learnings file (project-internal, Tier-1) derives "86% cached tokens" from these numbers; note the raw archived figures imply ~98% of input tokens are cached reads (68,000 of 68,790 input tokens), so the 86% figure is a conservative derivation - either way, cached reads dominate the request and are billed at the discounted cached-read rate ($0.0028/1M on Go, matching DeepSeek direct) (sources/opencode-go-docs.md; project-internal learnings file).
- **Cost asymmetry worst-case for this project**: on the Go subscription, a mid-conversation DCP prune invalidates the cached prefix from that point forward; every subsequent request re-sends the mutated prefix at miss price. Because ~86-98% of input tokens are cached reads, a ~5% cache-hit degradation (85% vs 90%) flips roughly 5% of input tokens from $0.0028 to $0.14 per 1M - a 50x unit-cost swing on that slice, recurring on every request after each prune. DCP's own dedup/purgeErrors recalculate only on compress-tool use, so cache impact is coupled to compression events (sources/dcp-github-readme.md). The README's "no impact" carve-outs (request-based billing like GitHub Copilot; uniform token pricing like Cerebras) do NOT apply to this project's DeepSeek/Go usage (sources/dcp-github-readme.md).

## 4. No cache-preserving mode exists

- **README prefix-invalidation statement**: DCP's own documentation states pruning "changes messages, which invalidates cached prefixes from that point forward" - the mechanism is inherent to the design, not a misconfiguration (sources/dcp-github-readme.md).
- **turnProtection protects the newest, not the prefix**: `turnProtection` (enabled default false, turns default 4) protects recent tool outputs from pruning for N turns past tool invocation - it shields the TAIL of the conversation, not the cached prefix. It cannot preserve the prefix because the prefix is exactly the older content DCP compresses (sources/dcp-schema.json; sources/dcp-github-readme.md).
- **manualMode / deny are disable-only levers**: `manualMode.enabled` disables autonomous context management (tools only run via /dcp commands), but `manualMode.automaticStrategies` (default true) keeps deduplication/purgeErrors running even in manual mode - and those strategies also mutate messages (dedup keeps only the most recent output of repeated calls), so manual mode does not stop prefix mutation. `compress.permission: "deny"` unregisters the compress tool; `enabled: false` disables the plugin entirely. None of these preserve the cache while keeping DCP active (sources/dcp-schema.json).
- **Conclusion**: there is NO configuration that keeps DCP functional while preserving the prompt-cache prefix. The only cache-preserving options are disabling DCP entirely (enabled:false or removal) or switching to a tool designed for prefix preservation (headroom cache-mode, section 7).

## 5. Sleev: the successor (proxy architecture, cache-aware, proprietary, unverifiable, not drop-in)

- **DCP's own handoff**: "Development on DCP has slowed because most new context-management work has moved to Sleev and the `sleev` CLI. Sleev is a local proxy for Claude Code, Codex, and OpenCode that builds on DCP's core ideas with newer context-management features and will work with any harness/client." README recommends `npm i -g sleev` for fresh starts; v3.1.13 release notes confirm "Updated README guidance to point new users toward Sleev" (sources/dcp-github-readme.md, sources/dcp-releases.json).
- **Proxy architecture**: Sleev runs a local gateway - a proxy that transparently compresses the coding agent's conversation history to save tokens; it signs you in, installs and runs the gateway in the background, and points the harness (Claude Code, Codex, OpenCode) at it. Published npm releases include native (Rust) binaries (sources/sleev-npm-page.md, sources/sleev-ai-homepage.md, sources/sleev-ai-faq.md).
- **Cache-aware design**: "A lot of the engineering work in Sleev is about making sessions cheaper without casually destroying the cache behavior providers already offer." FAQ: "Cache hit rate is treated as a key optimization dimension, so Sleev avoids rewriting or removing context in ways that would break provider caching unless the expected savings justify it." Why-Sleev claims "Higher Hit Rates: In production tests - especially with OpenAI - Sleev-managed sessions often show higher cache hit rates than unoptimized sessions" and "Compound Savings" (fewer total tokens AND a higher percentage billed at discounted cached rates) (sources/sleev-ai-why-sleev.md, sources/sleev-ai-faq.md).
- **Proprietary / private repo**: npm metadata shows license "SEE LICENSE IN LICENSE.md" - PROPRIETARY (Sleev Labs Inc), with LICENSE.md/EULA.md/THIRD_PARTY_NOTICES.md shipped in the package; the repository `https://github.com/sleev-labs/sleev` returns 404 publicly (private repo) on both the GitHub web page and the API; no sleev repo appears in GitHub name searches (827 results, none relevant) nor in the DCP author's public repos; the Opencode-DCP org hosts only the DCP repo plus a request-logger. Weekly downloads 568, 82 versions, 0 dependencies, 0 dependents; collaborators include "spooon" (same npm handle as the @tarquinen/opencode-dcp maintainer) and sleeve-org (sources/sleev-npm-registry.json, sources/sleev-npm-page.md, sources/sleev-repo-meta.json, sources/sleev-github-search2.json, sources/tarquinen-repos.json, sources/opencode-dcp-org-repos.json).
- **Unverifiable claims**: sleev.ai marketing claims 65% average session-size reduction and 30% cheaper sessions (example: 329.9K tokens without Sleev vs 114.4K with), and 30-80% token-spend cuts per session - all vendor marketing (Med reliability per the manifest), with no public repo, no benchmarks, and no methodology to verify. The 404 private repo makes independent verification impossible (sources/sleev-ai-homepage.md, sources/sleev-ai-why-sleev.md).
- **Not drop-in**: Sleev is a proxy, not an OpenCode plugin - the harness must be pointed at the local gateway (config changes), and licensing restricts use: solo commercial work allowed for one person, organization evaluation limited to 15 days/one account/one machine/non-production, regular team use requires pilot/enterprise/written agreement, no SLA without enterprise agreement. Privacy: conversation data is NOT sent to Sleev servers by default; account/install/licensing/usage metadata is (sources/sleev-ai-faq.md, sources/sleev-npm-page.md).

## 7. Alternatives ranking

1. **headroom cache-mode (best candidate)**: CacheAligner "detects and warns about volatile content that can bust provider KV cache prefixes; never rewrites prompts" (read-only drift detector); live-zone compression "compresses only new bytes (fresh tool output, latest turn); frozen prefix stays byte-identical so provider cache is not busted. History is never dropped." `headroom wrap opencode` is supported; Apache 2.0 open source; local-first. CAVEAT: prefix preservation through the opencode-go proxy endpoint (opencode.ai/zen/go/v1/*) is UNVERIFIED - that is the DIA-183 feasibility spike's job (pending) (sources/headroom-github-readme.md; project-internal DIA-183 learnings).
2. **Sleev**: cache-aware by design (cache hit rate treated as a key optimization dimension) and the DCP author's own successor, but proprietary with a private repo, unverifiable marketing claims, proxy architecture that is not drop-in, and licensing constraints for team use (section 5).
3. **DCP (status quo)**: documented ~5% cache-hit degradation with no measured benefit, no cache-preserving mode, a 67-issue cache-tagged bug surface including silent load failures, and slowed development (sections 2-4).
4. **Plain compaction (native)**: the fallback baseline; static whole-session compaction at max context; no DCP-specific benefit evidence exists in the archived sources.

## 8. EBDV evidence basis (DIA-115 variants)

- **V1 - remove DCP entirely (supported)**: DCP's own README documents the ~5% cache-hit degradation (85% vs 90%) with no measured upside; no cache-preserving mode exists (section 4); the 50x miss/hit asymmetry makes the degradation a recurring cost on a request profile where ~86-98% of input tokens are cached reads (section 3); native compaction remains as fallback; zero bats assertions depend on DCP; the removal surface is enumerable (6 touchpoints + validator coupling, section 6). Evidence: sources/dcp-github-readme.md, sources/deepseek-pricing.md, sources/opencode-go-docs.md, sources/dcp-schema.json.
- **V2 - keep DCP but disable/configure pruning (supported as conservative alternative)**: `enabled: false` or `compress.permission: "deny"` stops pruning while keeping the plugin installed; but manualMode still runs automaticStrategies (dedup/purgeErrors) by default, which also mutate messages, so a true cache-preserving disable requires enabled:false or removal; keep-but-disable retains the plugin surface (autoUpdate, load-failure risk per section 2 bugs) with no benefit. Evidence: sources/dcp-schema.json, sources/dcp-cache-issues.json.
- **V3 - replace DCP with Sleev or headroom cache-mode (premature)**: Sleev is proprietary/private with unverifiable claims and is not drop-in (section 5); headroom cache-mode prefix preservation on the opencode-go endpoint is UNVERIFIED pending the DIA-183 spike (section 7). Replacement should wait for the spike result. Evidence: sources/sleev-npm-page.md, sources/sleev-ai-faq.md, sources/headroom-github-readme.md.
- **V4 - abort/status-quo (not recommended)**: accepts the documented ~5% cache degradation with no measured benefit and no cache-preserving mode. Evidence: sources/dcp-github-readme.md.
- **Recommendation basis**: V1 is the evidence-supported primary (documented degradation, no upside, no preserving mode, clean fallback, enumerable removal surface); V2 is the conservative fallback if the developer wants a reversible first step; V3 is premature until the DIA-183 spike verifies headroom on the Go endpoint. The final EBDV decision with because-justification is recorded in the DIA-197 ticket by the orchestrator.
