## 1. Державні автомати для поведінки агентів <a id="1-дер-автомати"></a>

### Ключовий механізм

Кінцевий автомат (FSM) моделює поведінку агенту як набір обмежених станів з детерміністичними переходами між ними. Кожен стан визначає "як" машина поводиться; кожен перехід відбувається за чітко визначеною подією (Stately AI).

XState реалізує цей патерн через ієрархічні стейт-чарти: стани можуть вкладатися один в одного, утворюючи деревоподібну структуру. Початковий стан визначається властивістю `initial`, а фінальний -- властивістю `type: "final"`. Ключове обмеження: "неможливі стани" (одночасне заповнення форми та її надсилання) виключаються самою моделлю (Stately AI).

Паралельні стани (parallel regions) дозволяють кілька незалежних аспектів системи бути активними одночасно. Вхід у паралельний стан активує всі регіони; вихід -- деактивує всі. Подія, отримана в паралельному стані, одночасно обробляється всіма регіонами. Значення стану стає об'єктом зі значеннями кожного регіону. Перехід між регіонами слід уникати; синхронізація -- обов'язкова (Stately AI).

### Застосовність до агентів

- Агент як стейт-машина: кожен агент -- це актор XState з власними станами (idle, working, waiting, error).
- Батьківський агент може викликати дочірнього агента як child-актора з типізованим вводом та виводом.
- Паралельні регіони дозволяють агенту одночасно виконувати кілька незалежних аспектів (наприклад, моніторинг + обробка).
- Fan-out через `enq.spawn` створює видимих дочірніх акторів з незалежним прогресом.

> **Цитата:** "An agent machine is an XState actor, so you compose agents with XState's existing actor patterns. No separate orchestration layer" (Stately AI, "Multi-agent composition").

## 2. Проектування за контрактами <a id="2-контракти"></a>

### Ключовий механізм

Design by Contract (DbC) формалізує угоди між компонентами через три елементи:

- **Предумови (preconditions)** -- умови, які мають виконуватися перед викликом функції. Реалізуються через `.precondition([])`.
- **Постумови (postconditions)** -- умови, які гарантуються після успішного виконання. Реалізуються через `.postcondition([])`.
- **Класові інваріанти** -- умови, що мають виконуватися завжди (до/після кожного публічного методу). Реалізуються як публічний `const` метод `invariant()`.

Boost.Contract використовує RAII-об'єкт `boost::contract::check` для автоматичного захисту контрактів. Старі значення зберігаються через `BOOST_CONTRACT_OLDOF(x)` для перевірки постумов (Boost).

### Застосовність до агентів

- Контракти забезпечують детермінізм: якщо предумова виконується, результат визначений.
- Інваріанти гарантують, що агент після кожної операції залишається у "валідному" стані.
- Виняткові гарантії (`except`) визначають поведінку при порушенні контракту -- критично для відновлення після помилок.

> **Цитата:** "When exception guarantees are specified, they are programmed using a functor passed to `.except(...)`" (Boost, "Contract Tutorial").

## 3. Патерни передачі повідомлень <a id="3-повідомлення"></a>

### 3.1. Ідемпотентний споживач

**Ключовий механізм:** Споживач повідомлень має бути ідемпотентним -- результат обробки одного й того ж повідомлення кілька разів має бути ідентичним обробці одного разу. Реалізація: записування ID оброблених повідомлень у таблицю `PROCESSED_MESSAGES` з первинним ключем `(subscriberId, messageID)`. При дублюванні `INSERT` завершується помилкою, транзакція відкочується (Microservices.io).

### 3.2. Exactly-once семантика

**Ключовий механізм:** Kafka гарантує exactly-once через:

1. **Ідемпотентний продюсер** -- кожен продюсер отримує ID, дедуплікація через послідовний номер повідомлення.
2. **Реплікований лог** -- повідомлення вважається "закоміченим" тільки коли всі репліки ISR зафіксували його.
3. **Спожічі групи** -- кожен розділ (partition) споживається рівно одним споживачем у межах групи.

> "Kafka's semantics are straightforward. When publishing a message we have a notion of the message being 'committed' to the log" (Kafka, "Design").

### Застосовність до агентів

- Агенти, що обробляють повідомлення, мусять бути ідемпотентними: повторна обробка не змінює стан.
- Використання ідемпотентних ключів (`workflow_run_id + activity_id`) для зовнішніх сервісів (Temporal).
- Реплікований лог як примітив для побудови агентних систем у стилі state-machine replication.

## 4. Оркестрація проти хореографії <a id="4-оркестрація"></a>

### Ключовий механізм

Saga-патерн реалізує транзакції, що охоплюють кілька сервісів, без розподілених транзакцій. Два підходи координації:

**Хореографія:** кожна локальна транзакція публікує доменні події, які запускають наступну. Простіше для реалізації, але складніше для відстеження (Microservices.io).

**Оркестрація:** оркестратор (об'єкт) каже учасникам, які локальні транзакції виконувати. Більш явний контроль, але додаткова точка відмови (Microservices.io).

**Компенсуючі транзакції:** при помилці виконуються зворотні дії для скасування попередніх змін.

### Temporal: тривале виконання

**Ключовий механізм:** Temporal реалізує "durable execution" -- визначення робочого процесу (Workflow Definition) визначає обмеження виконання. Код робочого процесу має бути **детерміністичним**: при однаковому вводі він має генерувати ту саму послідовність API-викликів (Temporal).

**Розподіл нелінійної логіки:** операції, що порушують детермінізм (API-виклики, LLM, БД), виносяться в Activities, які виконуються поза шляхом replay. Activities мають at-least-once семантику та автоматичні повтори (Temporal).

**Типи помилок:** `ApplicationError` (бізнес-логіка), `ActivityError` (обгортка), `TimeoutError`, `CancelledError`, `TerminatedError`. Розрізнення transient vs intermittent vs permanent помилок для налаштування політики повторів (Temporal Python).

### Застосовність до агентів

- Оркестрація агентів: централізований оркестратор керує порядком виклику підагентів.
- Хореографія агентів: агенти координуються через події, без центрального контролю.
- Компенсуючі дії для відкату агентних транзакцій.
- Детермінізм Workflow Definition = детермінізм агентного процесу.

> **Цитата:** "A Workflow Definition can not have inline logic that branches based off a local time setting or a random number" (Temporal, "Workflow Definition").

## 5. Патерн "електричний вимикач" (Circuit Breaker) <a id="5-circuit-breaker"></a>

### Ключовий механізм

Трифазний кінцевий автомат:

| Стан | Поведінка |
|------|-----------|
| **CLOSED** | Запити проходять нормально; облік помилок |
| **OPEN** | Всі запити негайно відхиляються з `CallNotPermittedException` |
| **HALF_OPEN** | Обмежена кількість тестових запитів для перевірки відновлення |

**Переходи:** CLOSED -> OPEN (при перевищенні порогу помилок або повільних викликів); OPEN -> HALF_OPEN (після `waitDurationInOpenState`); HALF_OPEN -> CLOSED (тестові запити успішні) або HALF_OPEN -> OPEN (невдача).

**Налаштування (Resilience4j):**
- `failureRateThreshold` (50%) -- поріг частки помилок
- `slowCallRateThreshold` (100%) -- поріг повільних викликів
- `slidingWindowSize` (100) -- розмір скользючого вікна
- `minimumNumberOfCalls` (100) -- мінімум викликів перед розрахунком

Скользюче вікно: count-based (кількість вимірів) або time-based (часові бакети). Snapshot отримується за O(1) завдяки попередньому агрегуванню (Resilience4j).

### Застосовність до агентів

- Агент-проксі: виклики зовнішнього сервісу через circuit breaker.
- Попередження каскадних відмов: якщо один агент недоступний, інші не витрачають ресурси на очікування.
- Тюнінг: значення timeout -- компроміс між хибними спрацюваннями та надмірною затримкою.

> **Цитата:** "When the number of consecutive failures crosses a threshold, the circuit breaker trips, and for the duration of a timeout period all attempts to invoke the remote service will fail immediately" (Microservices.io, "Circuit Breaker").

## 6. Детерміністичний роутинг <a id="6-роутинг"></a>

### Ключовий механізм

Istio реалізує роутинг через VirtualService + DestinationRule. Три типи правил:

- **Content-based** -- маршрутизація за вмістом запиту (URI, схема, метод).
- **Header-based** -- маршрутизація за HTTP-заголовками (наприклад, `end-user: jason`).
- **Weight-based** -- розподіл трафіку за відсотками між версіями сервісів.

Порядок правил -- визначальний: перше відповідне правило застосовується. DestinationRule застосовується **після** VirtualService.

**Механізми мережевої стійкості:** таймаути, повтори з exponential backoff, circuit breakers на рівні з'єднань (`maxConnections: 100`), ін'єкція помилок (delays, aborts) для тестування (Istio).

### Застосовність до агентів

- Роутинг повідомлень між агентами за змістом або заголовками.
- Ваговий розподіл навантаження між екземплярами агентів.
- Fault injection для тестування стійкості агентної системи.

## 7. Формальна верифікація <a id="7-верифікація"></a>

### Ключовий механізм

**Design by Contract як формальна верифікація:** Boost.Contract реалізує формальні гарантії на рівні компілятора. Предумови, постумови та інваріанти перевіряються автоматично; порушення генерує асерт. Це не model checking у строгому сенсі, але забезпечує формальну коректність на рівні поодиноких компонентів.

**Кінцеві автомати як модель:** Resilience4j та XState моделюють поведінку як формальні FSM з обмеженими станами та переходами. Це дає змогу аналізувати можливі стани системи та виключати "неможливі" конфігурації.

**Практичні обмеження:**
- Формальна верифікація (Z3, model checking) ефективна для малих, ізольованих компонентів.
- Для складних розподілених агентних систем повна верифікація комбінаторно вибухає.
- Компроміс: дизайн за контрактами + тестування + спостереження замість повного model checking.

### Застосовність до агентів

- Контракти для кожного агентного "інтерфейсу" (вхід/вихід).
- FSM-моделі для верифікації можливих переходів станів агента.
- Обмеження: повна верифікація multi-agent систем -- предмет дослідження, не інженерна практика.

## 8. Спостережувані та керовані стани <a id="8-спостереження"></a>

### Ключовий механізм

Temporal розрізняє **Workflow API**, що генерують **Commands** (керовані дії), та API, що не генерують Commands (спостереження). Commands визначають, що створює Event History:

- **Керовані (Commands):** запуск таймерів, планування Activity/Child Workflow, надсилання Signals.
- **Спостережувані (non-Commands):** отримання поточного часу, генерація випадкових чисел, зчитування з ненадійних ресурсів.

Ключове правило: Commands не можуть бути перестворені, додані або видалені без Versioning. Некеровані API можуть вільно змінюватися (Temporal).

**XState: два механізми спостереження:**
- `onTransition` -- тільки кореневий автомат (керований перегляд).
- `inspect` -- потік подій всієї системи, включно з дочірніми акторами (повний перегляд).

### Застосовність до агентів

- Розділення Query (читання стану) та Signal (зміна стану) для агентів.
- Спостереження за прогресом дочірніх агентів через inspect.
- Версіонування агентних Workflow для сумісності з попередніми версіями.

> **Цитата:** "Workflow code must be deterministic to support replay. To handle non-deterministic operations like API calls, LLM/AI invocations, database queries, and other external interactions, put them in Activities" (Temporal, "Workflow Definition").

## 9. Висновки <a id="9-висновки"></a>

### Узагальнена таблиця патернів

| Патерн | Ключовий механізм | Агентна застосовність | Джерела |
|--------|-------------------|----------------------|---------|
| FSM / Statecharts | Детерміністичні стани та переходи | Моделювання агентів як акторів | Stately AI |
| Parallel regions | Одночасна активність кількох регіонів | Незалежні аспекти агента | Stately AI |
| Design by Contract | Предумови / постумови / інваріанти | Формальні гарантії інтерфейсів | Boost |
| Ідемпотентний споживач | Dedup через PROCESSED_MESSAGES | Безпечна повторна обробка | Microservices.io |
| Exactly-once | Ідемпотентний продюсер + ISR | Гарантована доставка | Kafka |
| Saga (хореографія) | Події між сервісами | Децентралізована координація | Microservices.io |
| Saga (оркестрація) | Централізований оркестратор | Явний контроль агентів | Microservices.io |
| Durable execution | Детерміністичний replay | Відновлювані агентні процеси | Temporal |
| Circuit breaker | 3-станний FSM + скользюче вікно | Захист від каскадних відмов | Resilience4j, Microservices.io |
| Роутинг | Content / header / weight rules | Маршрутизація повідомлень | Istio |
| Контракти vs верифікація | Формальні гарантії на рівні компонентів | Обмежена, але корисна | Boost, Resilience4j |
| Query vs Signal | Розділення читання та зміни стану | Спостереження за агентами | Temporal, Stately AI |

### Ключові висновки

1. **Детермінізм -- це обмеження, а не можливість.** Всі патерни працюють тому, що обмежують простір станів: FSM -- кількість станів, контракти -- вхід/вихід, exactly-once -- семантику доставки.

2. **Композиція агентів = композиція стейт-машин.** XState показує, що агенти складаються як актори: child actors, fan-out, executor inheritance -- без додаткового оркестраційного шару.

3. **Ідемпотентність -- фундамент.** Ідемпотентний споживач, ідемпотентний продюсер, ідемпотентні Activities -- все зводиться до: "результат не змінюється від кількості викликів."

4. **Оркестрація > хореографія для детермінізму.** Якщо потрібен передбачуваний порядок -- оркестратор. Якщо потрібна стійкість до відмов центральної точки -- хореографія.

5. **Circuit breaker = агентний імунітет.** Трифазний FSM запобігає каскадним відмовам; тюнінг порогів -- компроміс між чутливістю та стабільністю.
