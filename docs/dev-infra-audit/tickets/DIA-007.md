## Description

The `ai-specialist` agent (subagent, `qwen3.7-plus`, `edit` deny, `bash curl/wget`
deny) currently mixes two responsibilities: (a) researching best practices / external
sources and (b) curating resource manifests (AIHero-style config sources). The audit
plan proposed splitting it into `resource-manager` + `specialist`. This is a
**design decision** — follow the OpenCode-config change workflow (global AGENTS.md
§10: ai-specialist gate → user decides → design → implement → validate → register)
before acting.

## Planned Feature: Research Redispatch Resource Cycle (developer-gated DIA session redispatch; automatic redispatch deferred)

> Implemented 2026-08-03 via OpenSpec change dia-redispatch-cycle (design.md rule
> texts; .sdd/dia-redispatch-cycle/architecture.md ADR-001..005;
> openspec/templates/HANDOFF.md; NEXT-RUN.md §7). The owner requirements recorded
> below were the input; where the implementation refines them (automatic
> redispatch deferred; prognosis lives in HANDOFF.md as a section; crisis = C1–C5
> with no automated remediation), the implementation wins.

The DIA (dev-infra-audit) campaign should re-dispatch a new DIA session whenever
one is needed — redispatch is developer-initiated (the outgoing session hands off
via HANDOFF.md; the developer starts the successor; automatic redispatch was
deferred). Cycles continue, within the max-cycles budget (default 3), until one of
the following conditions is met:

1. An **independent clean re-audit with testing** is completed, OR
2. The cycle hits a crisis trigger (C1–C5 — e.g., >=3 same-task failures, re-plan
   churn, tool-call stagnation, context overflow, unresolved blocking prognosis)
   or exhausts its cycle budget.

**Loop structure (mandatory).** The redispatch loop MUST be structured as a
`while` loop condition with an `except`/crisis handler: when a **crisis** happens
(critical error loop, blocked progress), the cycle **breaks, stops, and the
situation is revisited to figure out what is wrong — with the human owner's
help**. The cycle must **not spin forever on its own**: crisis → stop → human
owner involvement.

**Decision/permission prognosis (recurs every cycle).**

- The session's final message is a HANDOFF.md whose "Prognosis for next cycle"
  section must include a prognosis of all user decisions and permissions needed
  for the NEXT session: the current session's final message forecasts/plans
  ahead — listing every decision and permission the next session will need (the
  protocol is general-purpose, not DIA-specific).
- The **NEXT session**, when it starts, **asks for all the needed decisions and
  permissions AT THE BEGINNING (up front)**, then does everything it can
  **autonomously on its own**.
- Each session also **prepares the plan of questions, decisions, and permissions
  required for the NEXT cycle redispatch** — so the decision/permission prognosis
  **recurs every cycle**.
