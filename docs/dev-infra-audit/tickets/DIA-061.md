## Description

**Summary:** after completing the full DIA-060 §10 workflow (Phase 1 research → Phase 4
implementation → Phase 6 review → C1/C2 fixes), the orchestrator declared "DIA-060 — Complete ✓"
and moved on without writing a handoff file. The developer had to explicitly prompt:
"y you not created a handoff?"

The Pre-Handoff Verification Gate (orchestrator operating rules) mandates:

> "before writing the handoff file (.opencode/session/current-handoff.json) with exit_state
> 'clean', the orchestrator MUST confirm ALL of: (a) make test-*... (b) lint...
> (c) typecheck... (d) openspec validate... (e) git status... (f) review disposition..."

But the orchestrator completed all work and simply stopped — it did not enter the gate-check
sequence. The handoff was only produced after the developer's explicit reminder.

**Root cause hypothesis:** the orchestrator interprets "task complete → respond to user" as
the terminal action. The handoff is treated as an optional extra step rather than a mandatory
gate. There is no hard trigger that forces the orchestrator to evaluate the Pre-Handoff
Verification Gate after every task cycle. The gate exists in the rules but requires the
orchestrator to self-initiate it — which it failed to do.

**Why this is a Blocker:** the handoff file is the bridge between sessions. Without it:

- The next orchestrator session has no batch-approval gate to present
- No record of what was done survives in structured form
- The restart-needed-for-permissions-change signal is lost
- Open tickets from the session are invisible at next boot

This is a core mechanism. It is not a feature refinement — it is the session-to-session
continuity contract. When it fails, the orchestrator loses all state between runs.

**Desired state:** after completing any non-trivial task cycle (multi-lane work, §10 workflow,
feature implementation, etc.), the orchestrator MUST:

1. Autonomously evaluate all 6 Pre-Handoff Verification Gates
2. Write `current-handoff.json` with appropriate exit_state (clean or manual-halt)
3. Present the handoff summary to the user

Before closing a session or declaring work "Complete ✓", the orchestrator must confirm:
"Have I written the handoff file?"

**Evidence of the gap:**

1. **DIA-060 completion (2026-08-07):** orchestrator completed a multi-phase §10 workflow
   spanning 4+ lanes (ai-specialist research, coder implementation, ai-specialist review,
   coder fixes C1/C2). This is exactly the kind of non-trivial task cycle that should trigger
   handoff. No handoff was produced.

2. **Developer had to prompt:** the orchestrator did not self-detect the omission. It required
   an explicit prompt from the developer to produce the handoff.

3. **Handoff was produced correctly when asked:** the mechanism works when triggered — the
   orchestrator CAN produce the handoff. The failure is not in the handoff-writing code but in
   the trigger: the orchestrator does not autonomously decide to write it.

**Related:** DIA-060 (orchestrator read scope missing tickets directory — the handoff file is
one of the files the orchestrator reads at boot to discover open tickets; both gaps compound).

**Implementation note (2026-08-07, §10 cycle — enforcement, not just prompting):** the
structural enforcement is now in place. (1) `scripts/validate-handoff.sh` gained a checksum
block: JSON handoffs (current-handoff.json) must carry a 64-hex SHA256 `checksum` that
matches the canonical serialization `jq -c '.prognosis | to_entries | sort_by(.key) |
from_entries'` — missing / empty / non-64-hex / placeholder (all-same-char) / mismatching
checksums are HARD failures. (2) `orchestrator_append.md` boot gate upgraded the checksum
step to a HARD GATE: mismatch/missing/non-64-hex → REFUSE TO RESUME, `log_decision`
(event_type 'handoff', resolution_status 'escalated', content_ref 'checksum-mismatch',
computed= vs stored=), escalate to developer, do NOT proceed; match → `log_decision`
(event_type 'handoff', resolution_status 'acknowledged', content_ref 'checksum-verified')
then batch approval. (3) The current handoff's stored checksum was NOT written in the
canonical form (stored 25646ee…, non-canonical) — it was recomputed to the canonical value
0eee533e… via the validator's `printf '%s'` no-trailing-newline method (`jq -c
'.prognosis | to_entries | sort_by(.key) | from_entries' | tr -d '\n' | sha256sum`). The
intermediate value 45a8404… was the raw-pipe (`jq | sha256sum`, trailing-newline-included)
computation, which is NOT the canonical form. The original trigger gap (orchestrator must
autonomously write the handoff) is addressed by
the hard gate: a missing/unverifiable handoff can no longer be silently resumed past.

## Fix

**Applied 2026-08-07 (§10 cycle)** — handoff checksum discipline, three layers:

1. **Validator rejection rules (`scripts/validate-handoff.sh`, new checksum block):**
   for JSON handoff files the block rejects, as HARD failures:
   - missing or empty `checksum` field → `FAIL: missing or empty 'checksum' field`
   - non-64-hex value → `FAIL: 'checksum' is not a valid 64-hex SHA256: <value>`
   - placeholder all-same-char values (`0{64}` / `f{64}` / `a{64}`) → `FAIL: 'checksum' is a placeholder (all-same-char)`
   - integrity mismatch → `FAIL: checksum mismatch (computed=<canonical>, stored=<stored>)`
   Integrity is verified against the CANONICAL serialization:
   `jq -c '.prognosis | to_entries | sort_by(.key) | from_entries'` (sorted keys, compact
   JSON) piped to `sha256sum`. Non-JSON inputs (the markdown reference template exercised
   by `make test-config` with no argument) skip the block, preserving the prognosis-schema
   gate (DIA-061 does not change the markdown template contract).
2. **Prompt HARD-GATE language (`.opencode/oh-my-opencode-slim/orchestrator_append.md`,
   boot-gate step 2):** on checksum MISMATCH / missing / empty / non-64-hex the orchestrator
   MUST refuse to resume, `log_decision` (event_type: 'handoff', resolution_status:
   'escalated', content_ref: 'checksum-mismatch', prognosis with computed= vs stored=),
   escalate to the developer, and NOT proceed until resolved; on MATCH it MUST `log_decision`
   (event_type: 'handoff', resolution_status: 'acknowledged', content_ref:
   'checksum-verified') and then proceed to batch approval. The surrounding gate steps
   (detection → present → approve → C5 check → VERIFICATION acknowledgement) are intact.
3. **Checksum recompute:** the current handoff's stored checksum (25646ee…) was written by a
   non-canonical serialization and did NOT match the canonical form. The canonical stored
   value is 0eee533e…, computed with the validator's `printf '%s'` no-trailing-newline
   method (`jq -c '.prognosis | to_entries | sort_by(.key) | from_entries' | tr -d '\n' |
   sha256sum`); the intermediate raw-pipe value 45a8404… (`jq | sha256sum`,
   trailing-newline-included) is NOT the canonical form. The writer-side serialization
   (`.opencode/plugins/delegation-observer.ts` `computeChecksum`) was aligned in the Phase 6
   fix cycle (Finding 1) to this byte-identical contract (TS `Object.keys().sort()` +
   `JSON.stringify` == jq sorted-keys + `printf '%s'`), so future plugin-written handoffs
   match the validator.
