## Description

Developer-raised research request (2026-08-13). Current orchestrator session
records live in `.opencode/session/` (gitignored): registry.jsonl (~3.4k
lines, delegation lifecycle), messages.jsonl (~2.9k lines, semantic events),
derived messages.md (regenerated by `scripts/session-log render`),
current-handoff.json / HANDOFF.md (atomic write), ticker.json/.md,
gate-tokens/. All are written by the delegation-observer plugin
(`.opencode/plugins/delegation-observer.ts`) via silent `appendFileSync`
(per-row atomic) and read via FULL-FILE scans (delegation-observer.ts:337,379;
orchestrator recall/resume reads registry.jsonl for session_id lookup). The
session README states JSONL is a "WRITE-ONLY audit trail - append-only, not a
query database". This ticket requests research into replacing/supplementing
direct JSON file writes with a JSON-backed database and/or API layer
(lowdb / json-server / nedb / tinydb), evaluated on four axes:

1. **Visibility** - no query layer; messages.md is a shell-derived view
   (scripts/session-log render/stats/tail); ad-hoc questions (e.g. "which
   sessions are waiting?") require full-file reads.
2. **Reliability** - no locking, no schema validation, no corruption
   detection; cross-session interleaving risk under parallel orchestrator
   sessions (DIA-085). Failure history: DIA-068 (persistence trigger never
   fired - state-check regex mismatch), DIA-079 (handoff JSON parse error),
   DIA-075 (checksum mismatch).
3. **Determinism** - seq ids are monotonic per file but there is no
   cross-session global ordering guarantee; legacy messages rows lack row_id;
   no typed schema enforcement on append.
4. **Token economy** - reads are full-file into context (~6.3k JSONL lines
   today). A server-side filter/aggregation layer returns only the rows the
   consumer needs; derived views (messages.md) are rendered on demand instead
   of being read raw.

**Hypothesis to test, not assert:** "API interaction is faster, more
reliable, and cheaper than direct JSON file writes" - verify per axis with
measured evidence (representative read: full-file vs filtered, e.g. recall a
single session_id from registry.jsonl).

### Candidate matrix (EBDV-style, baseline as control)

- **lowdb** - embedded, atomic writes, query helpers, NO HTTP API (in-process
  query layer, not a server)
- **json-server** - REST API over JSON, but needs a separate running process
  (new infra in the docker dev container; orchestrator has no bash but could
  consume HTTP; plugin would need an HTTP client)
- **nedb** - embedded, MongoDB-like API, pure JS - **unmaintained** (last
  release ~2019), flag as risk
- **tinydb** - **Python-only**, mismatch with the TS plugin (delegation-
  observer.ts runs in-process Node); likely exclude with evidence
- **BASELINE (control)** - keep append-only JSONL + improve derived-view
  tooling (extend scripts/session-log), no new dependency

Per-candidate axes: visibility, reliability, determinism, token economy,
maintenance status, dependency weight (bundled into the plugin?), migration
cost from appendFileSync, concurrency safety, fit with the plugin hook
surface (tool.execute.before/after, event, experimental.session.compacting).

### Developer refinements (round 2, 2026-08-13)

D9 TICKET LEDGER ON THE SAME TOOLING: apply the same JSON-DB/API approach to
TICKET MANAGEMENT. Today the ledger is `docs/dev-infra-audit/tickets/*.md`
(human-readable by default, machine-parsed via YAML frontmatter by
`scripts/tickets` and by the delegation-observer ticket gate scanTickets,
delegation-observer.ts:430-436). The idea: store ticket data in the same
machine-readable JSON store (canonical source of truth), and generate the
human-readable .md views ONLY ON REQUEST (a `scripts/tickets render` analog
of `scripts/session-log render`), mirroring the messages.jsonl -> messages.md
derived-view pattern. Benefits to verify: single source of truth; queryable
frontier/blocked-by/lease state without md-frontmatter parsing; atomic
updates without frontmatter-edit races; token economy for orchestrator
ticket reads (path-scoped read of tickets/\* is currently full-file). Tradeoffs
to verify: the ledger is deliberately plain-text git-syncable for multi-device
work (COORDINATION.md section 1) - JSON is still text and stays git-syncable,
but the .md files become DERIVED artifacts (regenerated, never hand-edited),
and every frontmatter consumer (scripts/tickets rollup/new, delegation-
observer gate, COORDINATION.md claim convention) must switch to the JSON
store. The research MUST cover this migration cost explicitly, including the
lease/claim mechanics (session_id + lease_expires_at) in the JSON schema.

### Verified constraints

- JSONL/md files are the gitignored or git-synced source of truth; any
  replacement must preserve cross-session, cross-device semantics.
- Orchestrator read scope is path-locked to `.opencode/session/*` and
  `docs/dev-infra-audit/tickets/*` (+ archive) - a new store must stay inside
  these readable paths or extend the read scope (itself a section-10 change).
- The plugin runs in-process (Node): it can import libraries directly; it has
  no HTTP client today; json-server would require a process to manage.
- Existing consumers must keep working or be migrated: scripts/session-log,
  scripts/jsonl-stats.sh, scripts/tickets, the delegation-observer ticket
  gate, session.prompt recall by session_id.
- Any plugin / agent-prompt / config change is section-10-routable
  (ai-specialist gate -> developer decide -> design -> coder -> validate ->
  ai-auditor). Tooling-only changes (scripts) route via the dev-infra chain
  (spec -> implement -> test -> review).
