# Design: Reproducible Zod runtime for lifecycle RED-B

**Governing ticket:** DIA-260912-h8o5 "tests-infra: reproducible runtime for undeclared zod import"

**Ownership:** substance: developer; structure: AI; interview_depth: full; interview_reason: Developer confirmed Q1-Q10 before synthesis.

## Context

See `proposal.md` for motivation and scope. The root pnpm workspace includes only `apps/*` and `packages/*`; `.opencode/oh-my-opencode-slim` is a vendored Bun package outside that workspace. Its source imports `zod`, and its lifecycle RED seams are `src/utils/task-lifecycle.test.ts` plus `src/hooks/task-session-manager/index.test.ts`. The change remains within the existing package boundary and needs no architecture escalation.

## Goals / Non-Goals

**Goals:**

- Make the vendored package's test dependency graph deterministic from its own manifest and Bun lockfile.
- Reproduce the dependency restore in a disposable worktree before running the existing focused lifecycle seam.
- Distinguish a real RED-B assertion failure from bootstrap, resolution, and unexpected test failures.
- Preserve the instance and phase separation of DIA-260827-95fv by unblocking RED evidence only.

**Non-Goals:**

- No root pnpm dependency or root lockfile change.
- No test-framework change, production source change, or lifecycle-test assertion edit.
- No automatic install fallback, override, or package-manager substitution.
- No GREEN implementation or GREEN handoff for DIA-260827-95fv.

## Decisions

1. **Package-local dependency ownership:** Set `.opencode/oh-my-opencode-slim/package.json` `devDependencies.zod` to exact `4.3.6`, retain `peerDependencies.zod` as `^4.0.0`, and generate the package's Bun lockfile. The vendored package owns both imports and the Bun test runner; adding Zod to the root pnpm workspace would be an unrelated and non-reproducible workaround.
2. **Frozen clean-worktree verification:** Create a disposable worktree at the integrated RED fixed point, or a documented restored equivalent. In the package directory, run `bun install --frozen-lockfile`, then `bun run test:red-b`. This permits package-manager installation only from committed declaration and lock state; `bun add`, a current-worktree repair, and dependency overrides are prohibited.
3. **RED evidence contract:** Accept a nonzero Bun exit only when the named RED-B test executes and its assertion mismatch contains `state: return-channel-pending`, while the output contains no Zod module-resolution failure. A clean bootstrap followed by a passing test is invalid because it does not demonstrate the outstanding false-state defect.
4. **Fail-closed outcome:** Installation failure, absent test-body evidence, a passing test, a Zod resolution error, or any different failure ends verification without a fallback action. Success permits only RED-B rerun and evidence review; lifecycle GREEN stays blocked until that evidence is accepted.

### Approach

The implementation changes only the vendored package manifest and its Bun lockfile. The manifest includes a narrow `test:red-b` command for the two integrated lifecycle seams. The executor creates the isolated worktree, checks out the integrated fixed point or records the restored equivalent, uses Bun's frozen lockfile install, and executes that command. The report records the revision, commands, exit statuses, named assertion evidence, and absence of Zod resolution errors. No production code path performs an install or changes lifecycle behavior.

### Seams

- **Dependency declaration to Bun resolution:** `.opencode/oh-my-opencode-slim/package.json` plus generated Bun lockfile, exercised by `bun install --frozen-lockfile` in the isolated worktree.
- **Bun bootstrap to lifecycle RED:** the existing task-lifecycle and task-session-manager test-file entrypoints, exercised by `test:red-b`.
- **Lifecycle contract evidence:** the named test assertion expecting `state: return-channel-pending` for a cancelled receipt conflicting with a live Board record that lacks `cancellationRequested`. This is a DIA-260827-95fv RED seam, not implementation scope for this ticket.

## Risks / Trade-offs

- **A lockfile generated by a different Bun version may not be accepted by the runtime** -> use the project-supported Bun environment and fail closed rather than rewriting or bypassing the frozen install.
- **`b2012a3e` cannot contain the dependency repair** -> use a documented restored equivalent that preserves the RED-B test state and records its provenance.
- **The focused command could pass or fail before the assertion** -> require the named-test and assertion evidence; do not treat exit status alone as success.
- **A manual local repair can hide an incomplete dependency declaration** -> forbid `bun add`, overrides, and fallback installation; only the committed manifest and lockfile may satisfy resolution.

## Migration Plan

1. Change the package-local Zod development version to exact `4.3.6` and generate its Bun lockfile with the package's existing Bun workflow.
2. In a disposable worktree at the required fixed point or documented equivalent, run the frozen install and canonical focused Bun command.
3. Record the success criteria or fail-closed evidence. If valid RED evidence is produced, hand off only to DIA-260827-95fv RED-B evidence review.
4. To roll back, revert the manifest and Bun lockfile as one unit. Do not replace the rollback with a manual install or unlock GREEN work.
