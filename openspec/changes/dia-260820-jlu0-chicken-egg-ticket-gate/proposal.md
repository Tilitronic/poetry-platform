## Why

The DIA-217 ticket gate in `.opencode/plugins/delegation-observer.ts` (scoped to
`input.tool === "task"`, hard block at lines 2847-2861) requires every `task()`
dispatch to carry an unambiguous governing DIA ticket ID. The only working bypass
today is a pre-minted `[CAPABILITY: CAP-...]` token (minted by the orchestrator
via the `mint_capability` plugin tool, verified at line 2787, early-return at
2798).

This creates a chicken-and-egg deadlock: a brand-new ticket's ID is generated by
`scripts/tickets new` with a random suffix, so the `task()` that creates the
ticket cannot cite its own future ID. The weak-correlation path (lines
2905-2917) only allows a cited-but-not-yet-existing ID, which is impossible for a
fresh ticket (you do not have the ID yet). Therefore the ONLY working path to
create a ticket is for the orchestrator to pre-mint a capability token first; if
that step is forgotten, the gate blocks the very `task()` that would create the
ticket, and there is no recovery except manual token minting.

This is a recurring, workflow-blocking failure mode: ticket creation is the first
dispatch of nearly every campaign. The fix removes the deadlock by adding an
explicit meta-task carve-out inside the gate for ticket-creation /
procedural-authorization dispatches, while retaining the capability token as the
strong scoped path for other meta-operations (bootstrap, ai-infra-application).

## What Changes

- Add a meta-task detection block INSIDE the DIA-217 gate, immediately after the
  capability-token check (line 2805) and BEFORE the ticket_id resolution
  (line 2811) / hard block (line 2847). When the dispatch text (description +
  prompt) matches the meta-task whitelist, the gate allows the dispatch WITHOUT a
  ticket ID (early `return`, no hard block, no weak-correlation warn).
- Meta-task whitelist (substring match against the dispatch text):
  `scripts/tickets new`, `create ticket`, `procedural authorization`,
  `meta-task`, or the dedicated `[META-TASK]` marker.
- On carve-out, emit an audit row (`event: "meta_task_bypass"`) and a
  `tuiSafeWarn` noting the bypass, so the escape hatch is observable (same audit
  discipline as the capability-token path).
- Tighten the capability-token scope check at line 2787: change
  `if (result.valid)` to also require
  `result.payload && typeof result.payload.scope === "string"` (the token must
  name the capability it grants). This is defense-in-depth; all normally-minted
  tokens already carry a scope, so behavior is unchanged for legitimate tokens
  and a malformed/no-scope token is rejected instead of silently bypassing.
- Do NOT auto-mint tokens inside the gate. Do NOT add a separate carve-out for
  `bootstrap` / `ai-infra-application`; those meta-operations stay on the existing
  `[CAPABILITY: ...]` token path (they are not chicken-and-egg: the orchestrator
  pre-mints the token, then dispatches).

## Capabilities

### New Capabilities

None. This is a dev-infra / plugin-internal gate change. No spec-level capability
is introduced or modified.

### Modified Capabilities

None.

## Impact

- **Code:** `.opencode/plugins/delegation-observer.ts` gains a meta-task
  detection block (~15 lines) inside the `if (input.tool === "task")` gate, and
  line 2787's condition gains a scope presence check. No new functions; reuses
  the existing `dispatchText` assembly pattern and `appendRow` / `tuiSafeWarn`
  helpers.
- **Tests:** a new bats test file (or extension of the plugin's existing test
  harness) covering (a) a `task()` dispatch containing `scripts/tickets new`
  bypasses the gate without a ticket ID, (b) a dispatch containing `[META-TASK]`
  bypasses, (c) a dispatch containing only `create ticket` /
  `procedural authorization` / `meta-task` bypasses, (d) a normal dispatch without
  any whitelist signal and without a ticket ID is still hard-blocked, (e) a
  capability token with no `payload.scope` is now rejected (scope-leak closed).
- **APIs:** none new. The `mint_capability` plugin tool and `[CAPABILITY: ...]`
  marker contract are unchanged.
- **Dependencies:** none added.
- **Systems:** the DIA-217 ticket gate's failure mode (deadlock on ticket
  creation) is removed. Audit visibility is preserved via the `meta_task_bypass`
  row.

## Alternatives considered

- **Direction B - auto-mint a token inside the gate for ticket creation:**
  rejected - the gate must not mint secrets; token minting is an orchestrator
  privilege (the `mint_capability` tool is process-scoped, secret-bearing).
  Auto-minting inside the before-hook would couple the hook to secret generation
  and widen blast radius. Evidence: Tier-1 (in-repo `mint_capability` tool design
  at delegation-observer.ts:4837, scoped to orchestrator-only `reason` arg).
- **Direction C - widen the weak-correlation path to accept a "future" ticket ID
  placeholder:** rejected - the weak-correlation path (lines 2905-2917) is a
  warn-allow for a cited-but-absent ID; a placeholder is not a real ID and would
  let any dispatch claim a fake future ticket, defeating the gate's attribution
  purpose. Evidence: Tier-1 (gate design comment lines 2764-2771, strict tri-state:
  explicit-id > marked > literal > block).
- **Narrower meta-task whitelist (only `[META-TASK]` marker + `scripts/tickets
new`):** considered but not chosen - the developer approved the broader
  audit-literal whitelist (`scripts/tickets new`, `create ticket`,
  `procedural authorization`, `meta-task`, `[META-TASK]`) for ergonomics.
  Evidence: Tier-1 (interview Q1, developer-approved A1 signal set 2026-08-27).
- **Stricter scope binding (restrict ticket-gate bypass to a ticket-relevant
  scope allowlist, B2):** rejected in favor of B1 - full scope-to-operation
  binding across all gates is a larger change; the minimal presence check closes
  the concrete leak (a token without a scope) without re-plumbing the multi-gate
  token contract. Evidence: Tier-1 (interview Q2, developer-approved B1
  2026-08-27).
- **Separate carve-out for bootstrap / ai-infra-application (C2):** rejected -
  those are not chicken-and-egg (orchestrator pre-mints the token), so the
  existing token path already works; a second carve-out would widen the bypass
  surface for no deadlock benefit. Evidence: Tier-1 (interview Q3,
  developer-approved C1 2026-08-27).
- **Status-quo / do nothing:** rejected - the deadlock is a recurring,
  workflow-blocking failure (ticket creation is the first dispatch of every
  campaign). Evidence: Tier-1 (audit context: "if forgotten, the gate blocks the
  very task that would create the ticket -> deadlock").

Chosen option: Direction A (meta-task carve-out + B1 scope tightening + C1
token-path retention) - because it removes the ticket-creation deadlock with a
minimal, auditable escape hatch while keeping the strong scoped capability-token
path intact for other meta-operations.
